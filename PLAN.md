# Ubuntu Git GUI implementation plan

## Goal

Open an existing checkout and use the same Git configuration, credentials, and hooks that work from the terminal. The first release covers opening and cloning repositories, reviewing changes and history, staging, committing, creating and switching branches, fetching, pulling, pushing, and publishing a branch to a selected remote.

Use Tauri 2, Rust, and React with TypeScript and Vite. Ship an Ubuntu .deb first. Git comes from the host. Keep host-specific process and environment code in one place so more platforms can be added later.

## 1. Prove Git works from the Ubuntu launcher

- Scaffold the Tauri app and build a .deb with a thin, typed launcher test for Git discovery, fetch, and single-branch push. Fold those commands into the Git layer in phase 2. Check the target Ubuntu version and install the required Rust and WebKitGTK development tools during implementation. Git 2.43.0 is available on this host. Rust was absent from the inspected shell's PATH, and the WebKitGTK 4.1 pkg-config check did not succeed.
- Start with the desktop session's environment. Resolve Git and its child tools using that environment. Preserve the user's home and config paths, SSH agent, desktop session and keyring access, and configured credential helpers and signing programs. Keep ambient Git worktree and index overrides from redirecting operations away from the repository selected in the GUI.
- Offer a terminal launch command for users whose shell configures their toolchain. Add an Environment diagnostics view that reports Git and tool availability, versions, and the launch mode without displaying environment values or credentials. If launcher testing exposes a PATH mismatch, provide an optional user-managed PATH for Git and its children. Keep shell startup and runtime setup under the user's control.
- Zenurture's checkout uses HTTPS and the Git config includes a GitHub CLI credential helper. Let Git invoke its configured helper. Use the same approach for SSH, other HTTPS helpers, and non-GitHub remotes. The app needs no GitHub OAuth client or token store. Existing SSO, repository access, and branch rules still apply. Preserve configured askpass and pinentry behavior. For prompts that require a terminal, provide **Open in Terminal** at the checkout and show the equivalent operation with any secrets removed. Leave retry to the user, especially when a write may already have completed. Test first-time SSH host verification, a locked SSH key, signing, and expired HTTPS credentials. Keep credentials and debug traces outside the IPC contract, redact recognizable credential patterns in child output, and keep the bounded output buffer in memory only. Custom hooks control what they print. [Git credentials](https://git-scm.com/docs/gitcredentials), [GitHub CLI credential setup](https://cli.github.com/manual/gh_auth_setup-git), [GitHub OAuth app restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions)

**Exit check.** Open the packaged app from the Ubuntu launcher and verify Git and the Zenurture toolchain are visible. Run an explicitly initiated fetch against the existing org checkout using the configured HTTPS helper. Verify push through a branch and remote designated for testing. Use an isolated local bare remote for repeatable push and pull tests.

## 2. Build the Rust Git layer

- Put process execution and environment setup under `src-tauri/src/git/`, repository discovery and the open-repository registry under `src-tauri/src/repositories/`, and Tauri command handlers under `src-tauri/src/commands/`. These are proposed paths. Rust owns Git arguments, path validation, repository state, and output parsing. Generate TypeScript IPC bindings from Rust where supported by the chosen tooling and check for drift in CI. [Tauri commands](https://v2.tauri.app/develop/calling-rust/)
- Expose named operations such as `get_status`, `get_diff`, `stage_paths`, and `commit` over IPC. Use backend-registered repository IDs, typed inputs, and fixed Git commands with argument arrays. Treat paths as literal Git pathspecs and use argument delimiters where supported. Render Git output, filenames, and commit messages as text. Keep app-origin permissions tight and grant no general shell execution capability to the WebView. Opening a repository is an explicit user action since Git can run its configured helpers, filters, and hooks. [Tauri capabilities](https://v2.tauri.app/security/capabilities/)
- Discover the root and Git directories through `git rev-parse` so subfolders and linked worktrees open correctly. Key repository selection by worktree and serialize mutations by resolved common Git directory. Read status with `git status --porcelain=v2 --branch -z` and byte-safe parsing. Use `git --no-optional-locks status` for background refresh. Keep opaque path IDs for names that cannot round-trip as UTF-8. Handle staged and unstaged changes to the same path, renames, unborn branches, detached HEAD, conflicts, and missing upstreams. [Git rev-parse](https://git-scm.com/docs/git-rev-parse), [Git status](https://git-scm.com/docs/git-status)
- Run Git off the UI thread. Stream long operations over a Tauri channel with bounded output and separate completion status. Support cancellation of the operation's process group where safe and refresh from disk afterwards. A cancelled push can already have updated the remote. Mark that outcome as uncertain until the user verifies it. Handle Git lock failures from external tools without deleting lockfiles. Refresh after every write, including failures, and on window focus. Coalesce file notifications, lazy-load diffs, paginate history, and cap large diff output. Tag reads with repository and request IDs so old results cannot replace newer selections. [Tauri channels](https://v2.tauri.app/develop/calling-frontend/)

**Exit check.** Use temporary repository factories to cover linked worktrees, invalid and unusual paths, partial staging, detached and unborn HEAD, conflicts, failing Git commands, concurrent writes, stale reads, and cancellation. Run `cargo test --manifest-path src-tauri/Cargo.toml`.

## 3. Build the everyday workflow

- Give the app a persistent repository rail, branch and upstream status near the workspace title, and **Changes** and **History** views. For the light theme, use the frontend design skill's Swiss direction with cool white and gray surfaces, thin rules, and blue for the primary action. Offer a matching charcoal theme and follow the OS preference by default. Use sans-serif for navigation and monospace for diffs and output. Show selected files in a split diff view and keep a staged summary and commit form in a bottom tray. Include keyboard navigation, visible focus, and status labels alongside color.
- The Changes view separates staged and unstaged content and keeps the current Git index visible. Stage and unstage whole files first, then add hunk staging after the initial release. Use index-only unstage against HEAD, with a separate index-only path for an unborn branch. If Git refuses a removal from the index because of staged-only content, show that refusal and preserve the file. Support a commit summary and optional body. Keep the draft on failure and refresh the staged list and diffs to show edits made by hooks. The History view opens a commit and its changed files. Git owns index, commit, and signing behavior.
- Give each repository one context-appropriate main sync action. After checking divergence, show **Publish branch** for an eligible local branch that has never had an upstream, **Push** when ahead of the known push target, **Pull** when behind the upstream, or **Fetch** when there is no pending sync action. Show a deleted upstream as its own state. Keep explicit Fetch available and show when remote status was last checked. For pulls, use the active branch's single configured upstream with `--ff-only`. Show divergence with an **Open in Terminal** recovery path. [Git pull](https://git-scm.com/docs/git-pull)
- Resolve the push target independently from the pull upstream and show the named remote and branch before first use. Support one validated, explicit, non-force branch refspec with `--porcelain --no-follow-tags --recurse-submodules=check` so the app validates submodule commits without pushing them. Set the upstream only when the user publishes a branch and has selected its destination. For mirror, forced or multi-ref mappings, multiple push URLs, or destinations the app cannot resolve, direct the user to the terminal. Verify a fork checkout that fetches and pulls from upstream and pushes to a different remote. Verify that a configured tag or submodule push cannot publish extra refs and that a deleted upstream is never silently republished. Show a rejected push with Git's explanation. [Git push](https://git-scm.com/docs/git-push)
- Show clean, conflicted, operation-in-progress, missing-tool, and rejected-operation states. Keep progress visible while users read other repositories or history. Use a collapsible output panel for hook and Git messages, and keep it automatically open on failure. If Git refuses to switch branches because local edits would be overwritten, preserve those changes and surface the refusal.

**Exit check.** Verify from the packaged desktop app that a user can open and clone a repo, review changes, stage one file, make a commit, create a branch, fetch, push, pull, and publish to an explicit remote. Include keyboard navigation, theme switching, and long hook output. Unit-test frontend helpers and mappers only. Use temporary Git repositories created by test factories for Rust integration tests.

## 4. Qualify the release against Zenurture

The checkout has `core.hooksPath=.husky` with Husky 8, Node `22.21.0`, and pnpm `10.29.3` pinned by the repo. The Git child process must see these tools when launched from the desktop. Git dispatches hooks during normal commits and pushes. Keep the repository's hook configuration and exit behavior in charge. [Git hooks](https://git-scm.com/docs/githooks)

| Hook | What it runs | What to verify |
| --- | --- | --- |
| `pre-commit` | `pnpm exec lint-staged`, which runs Biome and can rewrite staged files | Show live output, then reread the index and working tree. Verify a partially staged file retains its unstaged edits. |
| `commit-msg` | `pnpm exec commitlint --edit "$1"`. Zenurture expects a conventional header with a ticket-number scope, for example `fix(ABC-123): update validation`. | Show the rule failure, keep the draft, and verify an accepted message creates one commit. |
| `pre-push` | commitlint over `origin/HEAD..HEAD`, then typecheck, lint, format check, and Fallow audit | Surface the first failure, keep the app usable throughout, and verify that a rejected hook leaves the target ref unchanged. |

Stage and commit against a disposable Zenurture checkout with its dependencies initialized and the remote-tracking `origin/HEAD` set for the hook's range. Use a writable local remote for the complete hook path, then qualify authenticated push on a designated test branch if available. Cover a regular repository with no hooks, a generic repository using Git's default hook location, and a custom hook path. Test missing Node or pnpm, first from the launcher and then with the user's working terminal environment. The session-manager PATH exposes Git, gh, Node, and pnpm here. Actual launcher inheritance and remote access still need end-to-end verification.

## Later releases

Add stash and conflict resolution as separate features with tests against real Git state. Add interactive rebase, submodule workflows, extra packaging formats, and GitHub API features only when needed. Keep host integrations behind separate commands so everyday Git operations remain usable on any remote the user's CLI can access.
